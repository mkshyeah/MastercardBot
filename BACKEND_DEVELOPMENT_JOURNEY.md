# Путь Разработки Бэкенда: От Идеи до Text-to-SQL API

Этот документ описывает ключевые этапы, решения и технические трудности, с которыми мы столкнулись при создании бэкенд-сервиса для хакатона.

---

### Фаза 1: Первоначальная Настройка и Планирование

1.  **Инициализация Проекта:**
    *   Создана структура проекта с разделением на `app` (основное приложение), `scripts` (вспомогательные скрипты) и корень проекта.
    *   Настроено виртуальное окружение Python (`enviroment_mastercard`) для изоляции зависимостей.
    *   Создан файл `requirements.txt` для управления пакетами.

2.  **Анализ ТЗ и Данных:**
    *   Проанализирован первоначальный план, техническое задание (ТЗ) и предоставленные данные.
    *   **Ключевое решение 1:** По просьбе произведена смена СУБД с PostgreSQL на **MySQL** для удобства локальной разработки.
    *   **Ключевое открытие:** Обнаружено серьезное расхождение между списком желаемых колонок (`example_database_columns.csv`) и реальной структурой данных в файле `example_dataset.parquet`. Было принято стратегическое решение ("Вариант А") работать с **реальными данными**, обогащая их при необходимости.

---

### Фаза 2: База Данных и Загрузка Данных

1.  **Проектирование Схемы БД:**
    *   На основе анализа `.parquet` файла спроектированы две таблицы:
        *   `transactions`: для хранения всех транзакционных данных (11.5 млн записей).
        *   `merchants`: в качестве справочника для `merchant_id` и их имен.
    *   Для реализации схемы использовалась библиотека **SQLAlchemy ORM**, модели описаны в `app/database/models.py`.

2.  **Скрипт Загрузки и Обогащения Данных (`scripts/populate_db.py`):**
    *   **Обогащение данных:** Реализован механизм для синтетической генерации колонки `authorization_status` ("Approved"/"Declined") на лету, так как она отсутствовала в исходных данных, но была критична для ТЗ.
    *   **Работа с большими данными:** Для обработки файла размером в 11.5 млн строк применен подход с **потоковой читкой данных** (`iter_batches` из `pyarrow.parquet`), чтобы избежать загрузки всего файла в оперативную память.
    *   **Оптимизация производительности:** Изначально загрузка данных в MySQL занимала >30 минут. Проблема была решена путем использования метода `method='multi'` при вызове `to_sql`, что позволило выполнять **пакетные вставки** вместо построчных и сократило время загрузки в разы.

---

### Фаза 3: Ядро API и Логика Text-to-SQL

1.  **Создание API на FastAPI:**
    *   Настроен основной каркас веб-приложения в `app/main.py`.
    *   Создан эндпоинт `POST /query` для приема запросов от фронтенда.

2.  **Эволюция Подхода к Генерации SQL:**
    *   **Первоначальная идея:** Создать простой SQL-конструктор, который бы собирал запрос из структурированного JSON, присылаемого фронтендом. Этот подход требовал от фронтенда сложной логики NLP-парсинга.
    *   **Стратегический поворот:** Было принято решение использовать **LangChain** для реализации всего Text-to-SQL конвейера. Это позволило нам "аутсорсить" сложнейшую задачу по пониманию естественного языка (NLP parsing) и генерации SQL (Query generation) мощной языковой модели.
    *   **Реализация:** В `app/services/sql_builder.py` была интегрирована `SQLDatabaseChain` из LangChain, которая напрямую подключается к нашей MySQL базе, анализирует ее схему и преобразует текстовый запрос пользователя в готовый к выполнению SQL.

3.  **Технические Трудности и Решения:**
    *   **Проблемы с OpenAI API:** Столкнулись и решили две проблемы: `429 insufficient_quota` (решено пополнением баланса) и `401 insufficient_permissions` (решено созданием нового API-ключа с полными правами).
    *   **Отладка LangChain:** Из-за быстрой смены версий библиотеки пришлось решить ряд `ModuleNotFoundError`. Также был написан специальный код для "извлечения" сгенерированного SQL-запроса из сложной структуры ответа `SQLDatabaseChain`.

---

### Фаза 4: Финализация API и Командная Работа

1.  **Упрощение API-контракта:**
    *   Благодаря мощи LangChain, API-контракт для фронтенда был **максимально упрощен**. Вместо сложного JSON, фронтенду теперь достаточно отправить только одно поле: `{"user_query": "текст вопроса"}`.

2.  **Настройка Git и GitHub:**
    *   Инициализирован локальный Git-репозиторий.
    *   Настроен `.gitignore` для исключения виртуального окружения и других служебных файлов.
    *   Внедрена **стратегия ветвления** (`develop` для стабильного кода, `feature/*` для новой разработки), чтобы обеспечить комфортную параллельную работу всей команды.

---

### Заключение

В результате был создан надежный и мощный бэкенд-сервис, который:
-   Работает с реальным, большим набором данных.
-   Предоставляет простой и понятный API.
-   Использует state-of-the-art инструменты (LangChain + LLM) для выполнения ключевой бизнес-задачи — преобразования естественного языка в SQL-запросы.
-   Готов к интеграции с фронтендом и демонстрации.
